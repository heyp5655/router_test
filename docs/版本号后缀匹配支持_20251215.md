# 版本号后缀匹配支持 - 2025-12-15

## 🎯 需求说明

**问题**: 固件文件名可能带有后缀（如 `35.3.0.11-a1.bin`），但测试配置中只配置主版本号（`35.3.0.11`），导致版本验证失败。

**需求**: 支持版本号前缀匹配，使带后缀的版本号能够通过验证。

---

## 📋 问题场景

### 固件文件命名
```
版本A: 35.3.0.10.bin          ← 无后缀
版本B: 35.3.0.11-a1.bin        ← 带后缀 -a1
```

### 测试配置
```python
self.version_a = "35.3.0.10"  # 版本A
self.version_b = "35.3.0.11"  # 版本B（只配置主版本号）
```

### 版本验证失败
当路由器显示版本为 `35.3.0.11-a1` 时：
- 期望版本: `35.3.0.11`
- 实际版本: `35.3.0.11-a1`
- 原逻辑: 严格字符串相等比较 → ❌ 不匹配

---

## ✅ 解决方案

### 修改版本比较逻辑

**文件**: `core/router_client.py:778-802`

**修改前**（严格相等）:
```python
# 步骤4: 对比版本号
if actual_version == expected_version:
    print(f"\n✅ 版本号匹配: {actual_version}")
    result["match"] = True
    return True, result
else:
    print(f"\n❌ 版本号不匹配！")
    ...
```

**修改后**（支持前缀匹配）:
```python
# 步骤4: 对比版本号（支持后缀匹配）
# 精确匹配或前缀匹配（实际版本以期望版本开头）
# 例如: 35.3.0.11-a1 可以匹配 35.3.0.11
if actual_version == expected_version or actual_version.startswith(expected_version + "-"):
    print(f"\n✅ 版本号匹配: {actual_version}")
    if actual_version != expected_version:
        print(f"   （前缀匹配成功，期望: {expected_version}, 实际: {actual_version}）")
    result["match"] = True
    return True, result
else:
    print(f"\n❌ 版本号不匹配！")
    ...
```

### 匹配规则

**匹配条件**:
1. **精确匹配**: `actual_version == expected_version`
2. **前缀匹配**: `actual_version.startswith(expected_version + "-")`

**匹配示例**:

| 期望版本 | 实际版本 | 匹配结果 | 说明 |
|---------|---------|---------|------|
| 35.3.0.11 | 35.3.0.11 | ✅ 匹配 | 精确匹配 |
| 35.3.0.11 | 35.3.0.11-a1 | ✅ 匹配 | 前缀匹配（带后缀-a1） |
| 35.3.0.11 | 35.3.0.11-rc1 | ✅ 匹配 | 前缀匹配（带后缀-rc1） |
| 35.3.0.11 | 35.3.0.11-beta | ✅ 匹配 | 前缀匹配（带后缀-beta） |
| 35.3.0.11 | 35.3.0.12 | ❌ 不匹配 | 版本号不同 |
| 35.3.0.11 | 35.3.0.11a1 | ❌ 不匹配 | 无分隔符"-"（避免误匹配） |
| 35.3.0.1 | 35.3.0.10 | ❌ 不匹配 | 版本号不同（避免部分匹配） |

## 🎯 关键设计考虑

### 1. 为什么使用 `startswith(expected_version + "-")`？

**目的**: 防止错误的部分匹配

**示例**:
- ✅ `35.3.0.11-a1`.startswith(`35.3.0.11` + "-") → True（正确）
- ❌ `35.3.0.110`.startswith(`35.3.0.11` + "-") → False（避免误匹配）
- ❌ `35.3.0.11a1`.startswith(`35.3.0.11` + "-") → False（无分隔符，避免误匹配）

**要求**: 后缀必须以 `-` 分隔，符合语义化版本规范

### 2. 保持向后兼容

**精确匹配优先**: 代码首先检查精确匹配，然后才检查前缀匹配

```python
if actual_version == expected_version or actual_version.startswith(expected_version + "-"):
```

- 如果版本完全相同，立即匹配
- 如果不完全相同，再检查前缀匹配

### 3. 详细的日志输出

**前缀匹配时的日志**:
```
✅ 版本号匹配: 35.3.0.11-a1
   （前缀匹配成功，期望: 35.3.0.11, 实际: 35.3.0.11-a1）
```

- 明确标识使用了前缀匹配
- 显示期望版本和实际版本
- 便于调试和追踪

## 🎓 语义化版本规范

### 版本号格式

**标准格式**: `major.minor.patch[-prerelease][+buildmetadata]`

**示例**:
- `35.3.0.10` - 标准版本
- `35.3.0.11-a1` - 预发布版本（alpha 1）
- `35.3.0.11-rc1` - 预发布版本（release candidate 1）
- `35.3.0.11-beta.2` - 预发布版本（beta 2）

**本次实现**: 支持 `-` 分隔的预发布版本后缀

## 🚀 使用建议

### 1. 配置版本号时的建议

**推荐做法**（只配置主版本号）:
```python
self.version_a = "35.3.0.10"  # 不包含后缀
self.version_b = "35.3.0.11"  # 不包含后缀
```

**原因**:
- ✅ 配置更简洁
- ✅ 支持带后缀的固件
- ✅ 支持无后缀的固件
- ✅ 更灵活

### 2. 固件文件命名建议

**可以使用的命名**:
- `35.3.0.10.bin` - 标准版本
- `35.3.0.11-a1.bin` - alpha版本
- `35.3.0.11-rc1.bin` - 发布候选版本
- `35.3.0.11-beta.2.bin` - beta版本

**要求**: 后缀必须以 `-` 分隔

### 3. 避免的命名

**不推荐**（会导致验证失败）:
- `35.3.0.11a1.bin` - 无分隔符
- `35.3.0.11_a1.bin` - 使用下划线
- `35.3.0.11.a1.bin` - 使用点号
