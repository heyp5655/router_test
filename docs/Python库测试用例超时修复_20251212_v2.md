## 问题回顾

经过第一次修复（添加 -u 参数）后，测试仍然失败。分析发现根本原因是：
- **"10秒无数据超时"判断过于严格**
- 即使添加了 -u 参数，Python脚本的网络通信（MQTT连接、Modbus查询）需要时间
- 原始成功实现使用的是**固定等待时间**，而不是"无数据超时"判断

## 最终解决方案（最简单有效）

参考原始成功实现（`D:\WK\Milesight\AUTO\设备python3.9模块脚本\pyserial_AUTO_test.py`），核心策略：
- **增加最大等待时间** (max_duration)
- **增加无数据超时** (no_data_timeout)
- 给测试脚本足够的时间完成所有操作

## 详细修改

### 1. paho_mqtt_library_test.py (第645-649行)

**修改前**:
```python

no_data_timeout = 20  # 如果20秒没数据，认为脚本结束
```

**修改后**:
```python
max_duration = 120  # 最多120秒（给足够时间完成MQTT连接和通信）
```

| **pyserial** | 30s → 120s | 10s → 30s |

## 修改原理

### 为什么这样修改有效？

1. **max_duration = 120秒**
   - MQTT需要时间建立连接（可能10-15秒）
   - Modbus需要多次查询（每次带超时）
   - 串口双向通信需要等待PC响应
   - 120秒足够完成所有这些操作

2. **no_data_timeout = 30秒**
   - 测试脚本可能在某些步骤暂停（等待连接、等待响应）
   - 30秒的无数据超时更宽松，允许这些正常的暂停
   - 仍然能检测到脚本真正卡死的情况

3. **原始成功实现的验证**
   - 原始代码在执行脚本后固定等待30秒（第1278行）
   - 我们的方案类似：给足够时间，不过早超时

## 后续建议

如果测试仍然不稳定，可以考虑：

1. **添加明确的结束标记**（如果需要更精确的控制）
   ```python

   if "###TEST_COMPLETE###" in self.test_output_buffer:
       print("检测到测试完成标记")
       break
   ```

2. **固定等待时间**（最简单粗暴）
   ```python

   ```
