## 问题描述

### 测试用例
- **名称**: 多设备反复升级稳定性测试 (ID 21)
- **测试目标**: 对两台路由器进行1000次固件升级循环
- **预期行为**: 两个进程并行执行，输出详细日志，完成所有升级
- **实际行为**: 多进程启动后立即退出，无任何子进程输出

### 错误现象

```
[2025-12-02 18:55:25] INFO - 启动多进程并行测试...
[2025-12-02 18:55:25] INFO - ✅ 两个进程已启动，正在并行测试...
```

**异常点**:
1. ❌ 没有任何子进程的日志输出
2. ❌ 测试只用了1.2分钟就"完成"（应该需要几个小时）
3. ❌ 没有任何升级操作的记录
4. ❌ 统计结果全部为0

## 根本原因分析

### 原因1: WebDriver对象无法序列化 🔴 **核心问题**

**技术细节**:
```python
# multiprocessing 使用 pickle 序列化参数
process1 = Process(
    target=_test_device_in_process,
    args=(
        self.device1_config,  # ✅ 可序列化（普通对象）
        "设备1",               # ✅ 可序列化（字符串）
        new_firmware,         # ✅ 可序列化（字符串）
        old_firmware,         # ✅ 可序列化（字符串）
        ...
    )
)
```

**问题所在**:
- `device_config` 参数会传递到子进程
- 子进程中创建 `RouterClient(device_config)`
- `RouterClient.__init__()` 会创建 `self.driver = webdriver.Chrome(...)`
- **Selenium WebDriver 无法被 pickle 序列化**
- 子进程启动失败，但没有任何错误提示

**验证方法**:
```python
import pickle
from selenium import webdriver

driver = webdriver.Chrome()
try:
    pickle.dumps(driver)  # ❌ 会失败
except TypeError as e:
    print(f"无法序列化: {e}")
```

### 原因2: Windows多进程模型的限制

**Windows vs Linux**:
- **Linux**: 使用 `fork()`，子进程继承父进程内存空间
- **Windows**: 使用 `spawn()`，子进程重新启动Python解释器
  - 必须重新导入所有模块
  - 需要 `if __name__ == "__main__"` 保护
  - 更容易出现循环导入问题

**当前代码缺陷**:
```python
# test_cases/stability/multi_device_firmware_upgrade_stability_test.py
# ❌ 缺少 if __name__ == "__main__" 保护

process1 = Process(...)
process2 = Process(...)
process1.start()  # Windows会重新导入当前模块
process2.start()  # 可能导致递归创建进程
```

### 原因3: pyautogui全局键鼠操作冲突

即使多进程能启动，也会面临：
```python
# 两个进程同时执行
进程1: pyautogui.hotkey('ctrl', 'v')  # 粘贴设备1的固件路径
进程2: pyautogui.hotkey('ctrl', 'v')  # 同时粘贴设备2的固件路径
# 结果：路径混乱，文件选择失败
```

**pyautogui限制**:
- 操作全局键盘和鼠标
- 无法区分目标进程/窗口
- 多进程同时调用会冲突

## 修复方案

### 方案选择

| 方案 | 优点 | 缺点 | 是否采用 |
|-----|------|------|---------|
| **串行模式** | 简单稳定，无序列化问题，避免键鼠冲突 | 测试时间翻倍 | ✅ 采用 |
| 修复序列化 | 保持并行，性能好 | 复杂，需传递配置而非对象，需在子进程创建driver | ❌ 不采用 |
| 多线程 | GIL影响小（大部分时间在等待） | pyautogui仍会冲突 | ❌ 不采用 |
| 远程WebDriver | 避免序列化问题 | 需要额外配置Selenium Grid | ❌ 不采用 |

### 采用方案: 串行测试模式

**核心思路**:
- 先完成设备1的所有升级循环
- 再开始设备2的所有升级循环
- 避免所有多进程/多线程问题

### 修改3: 添加_test_device()方法

```python
def _test_device(self, device_client: RouterClient, device_name: str,
                 new_firmware: str, old_firmware: str, stats: dict):
    """测试单个设备的固件升级循环"""
    start_time = time.time()

    for cycle in range(1, self.upgrade_cycles + 1):
        # 升级到旧版本
        success = self._upgrade_firmware(
            device_client, old_firmware, device_name, cycle, "旧版本"
        )
        if not success:
            stats["failed"] += 1
            stats["failed_cycles"].append(cycle)
            continue
        stats["success"] += 1

        # 升级到新版本
        success = self._upgrade_firmware(
            device_client, new_firmware, device_name, cycle, "新版本"
        )
        if not success:
            stats["failed"] += 1
            stats["failed_cycles"].append(cycle)
            continue
        stats["success"] += 1
        stats["total"] = cycle

        # 输出进度
        elapsed = time.time() - start_time
        self.log_info(f"[{device_name}] 进度: {cycle}/{self.upgrade_cycles}, "
                     f"成功: {stats['success']}, 失败: {stats['failed']}, "
                     f"耗时: {elapsed/60:.1f}分钟")
```

### 修改4: 添加_upgrade_firmware()方法

```python
def _upgrade_firmware(self, device_client: RouterClient, firmware_path: str,
                      device_name: str, cycle: int, firmware_type: str) -> bool:
    """执行单次固件升级"""
    try:
        self.log_info(f"[{device_name}] 循环 {cycle} - 开始升级{firmware_type}...")

        success = device_client.upload_and_upgrade_firmware(
            firmware_path=firmware_path,
            timeout=self.upgrade_timeout
        )

        if success:
            self.log_info(f"[{device_name}] ✅ {firmware_type}升级成功")
            return True
        else:
            self.log_error(f"[{device_name}] ❌ {firmware_type}升级失败")
            return False

    except Exception as e:
        self.log_error(f"[{device_name}] ❌ {firmware_type}升级异常: {e}")
        return False
```

## 性能影响分析

### 时间对比

| 模式 | 单次升级耗时 | 单台设备总耗时 (1000循环) | 两台设备总耗时 |
|-----|------------|-------------------------|--------------|
| **并行** | ~6分钟 | ~6000分钟 (100小时) | ~100小时 |
| **串行** | ~6分钟 | ~6000分钟 (100小时) | ~200小时 |

**实际影响**:
- ⚠️ 串行模式时间翻倍（100小时 → 200小时）
- ✅ 但稳定性大幅提升，避免各种冲突
- 💡 建议: 先用小循环次数测试（如10次）

### 优缺点对比

| 指标 | 多进程并行 | 串行模式 |
|-----|----------|---------|
| **速度** | ⭐⭐⭐⭐⭐ 快 | ⭐⭐⭐ 慢 |
| **稳定性** | ⭐⭐ 不稳定 | ⭐⭐⭐⭐⭐ 非常稳定 |
| **实现复杂度** | ⭐ 复杂 | ⭐⭐⭐⭐⭐ 简单 |
